## Вводная часть

### Что такое Edem Template
Это не просто Gulp-сборка, это объемный инструмент для верстальщиков, желающих ускорить свою работу и быть готовым к любым задачам на пути "хардкорной верстки".

### Основные возможности и преимущества

В шаблоне вы найдете множество скриптов-модулей, которые реализуют те или иные функции *(например: боковое меню, модальные окна, спойлеры, табы и прочее)*, готовые решения: настройки для VSCode, сниппеты, сочетания клавиш и тд. Это объемный "продукт", который потребует времени для ознакомления, но в итоге станет для вас незаменимым компаньоном.

### Краткая история создания
Меня зовут Роман Лебедев, я более семи лет занимаюсь веб-разработкой.  
Для верстки сайтов я достаточно долгое время использовал Gulp-сборку, которую собирал в 2019 году по видео с ютуба. С тех пор мой скилл подрос *(надеюсь)*, но одно оставалось неизменным - старая Gulp-сборка, которая моментами работала плохо. С выходом пятой версии Gulp руки наконец дошли до обновления.  
Несколько недель я потратил на настройку сборщика, поиск и дефектовку старых и новых зависимостей, переезд на новую систему импорта Sass, на ES-модули, переписывание устаревших скриптов, допиливание функционала, который давно был на карандаше и написание документации ко всему этому.  
И теперь мне не стыдно *(возможно)* и я могу представить свой "продукт" для общего пользования.  

*Вполне вероятно, что я мог упустить какие-то моменты в этой документации, но со временем мы все поправим!*

**С чего начать?**

## Установка и запуск

### Клонирование
Чтобы начать работу с шаблоном, необходимо склонировать этот репозиторий себе на устройство любым удобным способом.

### Интеграция зависимых файлов шаблона
Настройки редактора, сниппеты и список рекомендованных расширений лежат в папке `.vscode/` и применяются сами, как только вы откроете папку проекта в VSCode. При первом открытии VSCode предложит установить рекомендованные расширения — согласитесь *(список также открывается командой `Extensions: Show Recommended Extensions`)*.

Сочетания клавиш VSCode хранит только в настройках пользователя, поэтому для MacOS они поставляются профилем `.vscode/EdemGulpTemplateProfile_MacOS.code-profile`. В профиле — сочетания клавиш, настройка `"keyboard.dispatch": "keyCode"` для работы сочетаний в русской раскладке и те же рекомендованные расширения.

Чтобы подключить профиль:
- Перейти в профили *(Шестеренка управления ➔ Профили)*;
- В выпадающем меню рядом с кнопкой "Новый профиль" выбрать пункт "Импортировать профиль" и выбрать файл профиля;
- Нажать кнопку "Создать" снизу вкладки и дождаться завершения импорта;
- В списке профилей нажать на галочку рядом с EdemGulpTemplateProfile *(Использовать этот профиль для текущего окна)*.

Если вы хотите использовать профиль шаблона везде и всегда, установите галочку "Использовать этот профиль по умолчанию для новых окон" в настройках профиля EdemGulpTemplateProfile.  

[Подробнее о зависимых файлах шаблона здесь](#vscode-dependent).

### Установка зависимостей
В первую очередь необходимо подтянуть все зависимости командой `pnpm install` в терминале *(в корне проекта)*.  

*В шаблоне используется пакетный менеджер `pnpm` (преимущества гуглите), на него настроены все задачи сборки. <a href="https://pnpm.io/installation" target="_blank">Get started тут</a>.*  
> После выполнения данной команды будут загружены все необходимые для работы шаблона зависимости (папка node_modules).

**Требования к окружению:**
- Node.js 24 и выше *(версия зафиксирована в `.nvmrc` и `engines` в `package.json`; с `engine-strict` из `.npmrc` на старой версии установка не запустится)*. Выгрузка на сервер использует `process.loadEnvFile`;
- Файл `pnpm-lock.yaml` хранится в репозитории — так все форки и переустановки получают одинаковые версии пакетов. Для чистой установки используйте `pnpm install --frozen-lockfile`, а обновляйте зависимости осознанно *(`pnpm update`)* и коммитьте изменённый lock-файл;
- Список поддерживаемых браузеров задаётся полем `browserslist` в `package.json` *(по умолчанию `defaults`)*. По нему [lightningcss](https://lightningcss.dev/) расставляет вендорные префиксы и переводит современный CSS *(например, `color-mix()`)* в поддерживаемый этими браузерами вид.  

### Запуск сборки (режим разработки и продакшн)

#### Режим разработки (dev)
Режим разработки с запуском сервера запускается командой `pnpm dev`.
> Данная команда запускает ряд действий, благодаря которым будет работать шаблон, а именно:  
> - Запуск веб-сервера и синхронизации, благодаря которым мы сможем увидеть сайт в браузере и следить за изменениями без необходимости обновлять страницу *(страница с сайтом откроется автоматически по окончании выполнения команды)*.  
**Примечание:** по умолчанию сервер запускается на порту 3000, другой порт можно указать в `SERVER_PORT` в файле `.env` *(шаблон — `.env.example`)*. Если порт занят, browser-sync возьмёт следующий свободный.  
**Примечание:** вы можете открыть страницу с сайтом с любого другого устройства, подключенного к той же сети, что и ПК, на котором запущен шаблон. Для этого в консоли необходимо посмотреть нужный URL (для внешнего подключения), он будет озаглавлен как **External**. Например: `External: http://192.168.0.103:3002`.  
Это удобно, например, для проверки мобильной версии сайта с телефона *(не забудьте подключить телефон к Wi-Fi)*;
> - Будет собран облегченный dev-вариант проекта для разработки. Все собранные файлы помещаются в папку `build`. Именно содержимое этой папки отображается в браузере. Для CSS рядом создаётся карта кода `style.css.map` — в DevTools браузера видно, из какого SCSS-файла и строки пришло правило.

#### Сборка в продакшн (build)
Сборка в продакшн запускается командой `pnpm build`.
> - Данная команда запустит сборку продакшн-версии проекта, которая считается финальной и может быть передана заказчику;
> - **Чем отличается от dev-сборки?** Тут происходит ряд действий, которые просто не нужны в dev-сборке, а именно: оптимизация изображений, минификация JS и CSS файлов и еще несколько действий, которые облегчают финальный проект. Данная команда не запускает веб-сервер;
> - **Сброс кэша.** В продакшн-сборке к ссылкам на стили и скрипты в чанках `head.html` и `scripts.html` дописывается хэш содержимого файла: `css/style.css?v=581f8928`, `js/main.js?v=9fb63ab4`. Хэш меняется, только когда меняется файл, поэтому после деплоя браузеры посетителей сразу получают новые версии, а неизменённые файлы остаются в кэше. Для этого HTML в продакшн-сборке собирается после CSS и JS. Если вы подключаете стили или скрипты в своих чанках, используйте переменные `@@cssVersion` и `@@jsVersion` *(в dev они пустые)*;
> - **Ошибки.** В режиме разработки ошибка *(например, в SCSS или HTML)* показывается уведомлением, а сборка продолжает следить за файлами. В продакшн-сборке первая же ошибка выводится в консоль и останавливает сборку с ненулевым кодом выхода — так `pnpm run deploy` не выгрузит на сервер неполный билд;

#### Окружение сборки (stage и prod)
Помимо режима (dev/build) у сборки есть окружение, которое определяет, для какого сайта собирается проект:
- `stage` — тестовый сайт: в `<head>` выводится `<meta name="robots" content="noindex, nofollow">`, в подвале — dev-фреймы *(предупреждение о тестовом сайте и лейбл разработчика)*;
- `prod` — боевой сайт: всё перечисленное выше в сборку не попадает.

| Команда | Режим | Окружение |
| --- | --- | --- |
| `pnpm dev`, `pnpm dev:deploy` | dev | stage |
| `pnpm build`, `pnpm run deploy` | build | prod |
| `pnpm build:stage`, `pnpm deploy:stage` | build | stage |

Окружение можно задать вручную флагом `--env=stage|prod`, неизвестное значение останавливает сборку. В HTML-чанках оно доступно как переменная `env`:
```html
@@if (env !== 'prod') {
	<meta name="robots" content="noindex, nofollow">
}
@@if (env === 'prod') {
	<!-- счётчики аналитики и прочие скрипты только для боевого сайта -->
}
```
> В gulp-задачах окружение доступно как `app.env` и `app.isProd` *(объект `app` импортируется из `gulp/config/app.js`, пути — из `gulp/config/paths.js`)*.

### Остановка сборки
Чтобы остановить работу сервера (и режима разработки), необходимо в консоли *(где запущена сборка)* использовать стандартное сочетание клавиш `Ctrl+C|Control+C`.  

### <h3 id="lint">Проверка и форматирование кода</h3>
В шаблон встроены три инструмента:
- **ESLint** ищет ошибки в JS: необъявленные переменные, неиспользуемые импорты, пустые блоки. Настройки — `eslint.config.js`;
- **Stylelint** проверяет SCSS: неизвестные свойства и значения, ошибки в селекторах, устаревшую запись. Настройки — `.stylelintrc.json`, за основу взят `stylelint-config-standard-scss`;
- **Prettier** форматирует JS, SCSS, HTML и JSON: табы, одинарные кавычки, длина строки до 120 символов. Настройки — `.prettierrc.json`, исключения — `.prettierignore`. Директивы gulp-file-include (`@@include`, `@@if`) в HTML остаются на своих строках — за это отвечает плагин `gulp/plugins/prettier-file-include`.

Базовые правила отступов и переносов строк для любого редактора задаёт `.editorconfig`.

| Команда | Что делает |
| --- | --- |
| `pnpm lint` | запускает все проверки: ESLint, Stylelint и проверку форматирования |
| `pnpm lint:js` | только ESLint |
| `pnpm lint:scss` | только Stylelint |
| `pnpm format` | форматирует все файлы проекта |
| `pnpm format:check` | показывает файлы, которые не отформатированы, ничего не меняя |

Ошибки ESLint и Stylelint можно исправить автоматически, если они это допускают: `pnpm lint:js --fix`, `pnpm lint:scss --fix`.

С расширениями ESLint, Stylelint, Prettier и EditorConfig *(есть в рекомендованных)* ошибки подсвечиваются прямо в редакторе. В `.vscode/settings.json` Prettier назначен форматтером по умолчанию для HTML, JS, SCSS, CSS, JSON и YAML, поэтому команда `Format Document` *(`Shift+Alt+F|Option+Shift+F`)* форматирует файл так же, как `pnpm format`.

### <h3 id="ci">Автоматическая проверка и обновление зависимостей</h3>
**CI.** При каждом push в `main` и в каждом pull request GitHub Actions запускает `.github/workflows/ci.yml`: ставит зависимости из lock-файла *(`pnpm install --frozen-lockfile`)*, выполняет `pnpm lint`, собирает проект в окружениях `prod` и `stage`, а затем удаляет стартовую страницу и примеры командами `demo:remove` и `example:remove` и собирает проект ещё раз — так проверяется, что форк соберётся после подготовки к вёрстке. Результат виден на вкладке Actions и значком у коммита.

**Renovate.** Файл `renovate.json` настраивает бота [Renovate](https://docs.renovatebot.com/), который следит за новыми версиями пакетов и GitHub Actions и открывает pull request с обновлением:
- проверка идёт по понедельникам до 9 утра *(UTC)*;
- минорные и патч-обновления собираются в один pull request, мажорные приходят по одному — у них бывают несовместимые изменения;
- раз в месяц обновляется `pnpm-lock.yaml` целиком *(транзитивные зависимости)*.

CI проверяет каждый такой pull request, поэтому зелёный значок означает, что шаблон собирается с новой версией. Бот работает после установки [Renovate GitHub App](https://github.com/apps/renovate) на репозиторий; в форке подключите его так же, если хотите получать обновления.

### <h3 id="versions">Версии шаблона и обновление форка</h3>
Версия шаблона записана в `package.json` по [semver](https://semver.org/lang/ru/): `мажорная.минорная.патч`. Каждый релиз отмечен git-тегом вида `v1.5.0`, а что изменилось — описано в `CHANGELOG.md`, с пометками, что нужно перенести в форк.

Чтобы подтянуть изменения шаблона в форк, добавьте шаблон как второй remote и сравните версии:

	git fetch edem-gulp-template --tags
	git diff v1.4.0 v1.5.0 --stat

Список изменённых файлов подскажет, что переносить. Перенести всё разом можно слиянием — сниппет `gpf` вставляет команду `git pull --tags edem-gulp-template main --allow-unrelated-histories`.

### Выгрузка на сервер (SFTP)
В шаблон встроена выгрузка файлов на сервер по SFTP *(через SSH, порт 22)* — задача `gulp/tasks/deploy.js` на пакете `ssh2-sftp-client`. В отличие от обычного FTP она использует одно соединение, поэтому стабильно работает даже через VPN — FTP на двух соединениях (управляющем и передачи данных) через VPN и NAT часто рвётся. Внешние программы не нужны, работает на MacOS и Windows.

#### Настройка
1. Скопировать `.env.example` в `.env` и заполнить доступы: хост, порт, пользователь, путь к SSH-ключу *(рекомендуется)* и/или пароль. Файл `.env` не попадает в git.
2. Запустить выгрузку с пустым `DEPLOY_HOST_FINGERPRINT` — в консоли появится отпечаток ключа сервера. Сверить его с выводом команды `ssh-keyscan -p 22 ваш-хост | ssh-keygen -lf -` *(или с данными в панели хостинга)* и вписать в `DEPLOY_HOST_FINGERPRINT`. Без отпечатка выгрузка не запустится — это защита от подмены сервера.
3. В `deploy.config.js` указать, какие локальные папки и файлы в какие папки на сервере выгружать *(`local`, `remote`, `files`, `ignore`)* — по умолчанию там лежит пример для выгрузки `build/`, под конкретный проект пути нужно поправить.

#### Команды
- `pnpm dev:deploy` — обычный режим разработки + автовыгрузка. При старте на сервер догружаются файлы, изменённые с прошлой выгрузки, дальше каждый изменённый файл из `deploy.config.js` *(включая пересобранные gulp'ом файлы в `build`)* сразу отправляется на сервер;
- `pnpm run deploy` — продакшн-сборка *(окружение `prod`)* и выгрузка изменённых файлов из `deploy.config.js`;
- `pnpm deploy:stage` — то же самое, но с окружением `stage` *(noindex и dev-фреймы остаются)*, для выкладки на тестовый сервер.

> Сервер и пути выгрузки для всех команд берутся из одних и тех же `.env` и `deploy.config.js` — окружение влияет только на содержимое сборки.

#### Флаги выгрузки
Флаги дописываются после команды, например `pnpm run deploy --dry-run --delete`:
- `--dry-run` — показать, какие файлы будут выгружены *(и удалены, вместе с `--delete`)*, ничего не меняя на сервере;
- `--force` — выгрузить все файлы, а не только изменённые *(например, если файлы на сервере меняли вручную или выкладывали с другого компьютера)*. Работает и с `pnpm dev:deploy`;
- `--delete` — удалить на сервере файлы, которых больше нет локально. Удаляются только файлы внутри папок `remote`, подходящие под `files` и не попадающие под `ignore` цели из `deploy.config.js`. Перед удалением выводится список и запрашивается подтверждение в терминале; без терминала *(например, в CI)* нужен флаг `--yes`. Для `remote`, указывающего на корень сервера или домашнюю папку SSH-пользователя, удаление не выполняется. Пустые папки на сервере не удаляются;
- `--yes` — подтвердить удаление без вопроса.

> **Рекомендация:** перед первым `--delete` на проекте запустите его вместе с `--dry-run` и проверьте список — если `remote` настроен неверно, в список попадут файлы CMS.

#### Как это работает
> - **Только изменённые файлы.** Хэши выгруженных файлов хранятся в `.deploy-cache.json` *(отдельно для каждого сервера, файл не попадает в git)*. Файл выгружается, только если его содержимое изменилось с прошлой выгрузки на этот сервер;
> - **Атомарная замена.** Файл загружается во временный `имя.uploading` и заменяет старый одной операцией `posix-rename`, поэтому посетитель никогда не получит наполовину залитый `main.js` или `style.css`. Если сервер не поддерживает `posix-rename`, в консоли появится предупреждение и файлы будут заменяться удалением и переименованием;
> - Соединение держится открытым *(с keepalive)*, при обрыве *(например, переподключение VPN)* задача сама переподключается и повторяет операцию через 1, 2, 5, 10 и 20 секунд;
> - При ошибке доступа или несовпадении отпечатка сервера выгрузка останавливается — нужно исправить `.env` и перезапустить задачу;
> - Если параллельно используется VSCode-расширение SFTP с автозагрузкой, его стоит отключить, чтобы файлы не выгружались дважды.

### <h3 id="demo-example">Стартовая страница и примеры компонентов</h3>
В шаблоне два набора учебных материалов. Оба лежат в папках, имя которых начинается с подчёркивания.

| | Стартовая страница | Примеры компонентов |
| :--- | :--- | :--- |
| Что это | приветствие и чек-лист на `index.html`, заголовок в шапке, копирайт в подвале, оформление шапки, подвала и меню | страница `example.html` со ссылками на страницы отдельных компонентов: формы, табы, слайдер и другие |
| Где лежит | `src/html/_demo/`, `src/scss/_demo/` | `src/html/_example/`, `src/scss/_example/`, `src/js/_example/`, `src/img/_example/`, файлы `src/scss/example.scss` и `src/js/example.js` |
| Как собирается | входит в `style.css` слоем `demo` | отдельные `css/example.css` и `js/example.js`, их подключают только страницы примеров. В окружении `prod` страницы, стили, скрипты и картинки примеров не собираются |
| Как удалить | `pnpm run demo:remove` | `pnpm run example:remove` |

Стартовая страница нужна только до начала вёрстки. Примеры можно держать в проекте всё время разработки: их оформление лежит в слое `example` ниже `components`, поэтому стили проекта его перекрывают, и страницы примеров показывают компоненты уже в оформлении проекта.

Команды удаления выводят список папок и файлов, из которых будут убраны подключения *(`@@include` в чанках, подключение стилей и имя слоя в `main.scss`)*, и спрашивают подтверждение. Без терминала нужен флаг `--yes`: `pnpm run demo:remove --yes`. Если в этот момент запущен `pnpm dev`, перезапустите его.

**Свой пример** добавляется так:
- страница `src/html/_example/example-<имя>.html` по образцу соседних и ссылка на неё в `example.html`;
- стили — файл в `src/scss/_example/`. Индекс этой папки генерируется так же, как в `components/`, прописывать файл не нужно;
- скрипт — модуль в `src/js/_example/` и его вызов в `src/js/example.js`.

Страница примеров подключает свои стили и скрипты параметром `example: true`:
```html
@@include('../chunks/head.html', {title: 'Примеры: табы', example: true})
@@include('../chunks/scripts.html', {example: true})
```

### Как я начинаю верстку
- Накидываю стили для стандартных компонентов сайта *(кнопки, заголовки и прочее)*;
- Далее перехожу к верстке страниц, начиная с главной *(страницы лежат по пути `src/html/pages/`)*. Строю структуру поблочно;
- После каждого блока перехожу к стилям для этого блока и его компонентам *(заранее определяя, есть ли подобные компоненты на сайте)*;
- Сразу делаю адаптив для блока;
- Перехожу к следующим блокам и повторяю шаги.

Файлы стилей уникальных блоков *(которые встречаются один раз на всем сайте)* помещаю в папку `src/scss/layout/`.  
Файлы стилей компонентов помещаю в папку `src/scss/components/`.  
Не забываем в начале каждого нового файла стилей подключать абстракции `@use 'abstracts' as *;` *(быстро добавить эту строку можно сниппетом `as`. Подробнее в разделе [Сниппеты](#сниппеты))*.  
Файлы стилей, которые вы помещаете в `src/scss/layout/` и `src/scss/components/` не нужно нигде прописывать, они генерируются автоматически силами сборки.  

Для быстрого создания файлов использую VSCode-расширение File Utils *(сочетание клавиш `Ctrl+Alt+N|Option+Command+N`)*.
Для навигации и поиска файлов использую встроенные функции VSCode *(сочетание клавиш `Ctrl+Shift+F|Command+Shift+F`)*.
Для быстрого поиска нужных стилей по классу так же использую встроенные функции VSCode *(сочетание клавиш `Ctrl+T|Command+T`)*.
Подробнее о сочетаниях клавиш и возможностях шаблона с ними в разделе [Сочетания клавиш](#сочетания-клавиш).  

Если вам нужен пример компонента или модуля шаблона, то их можно найти на странице с примерами `src/html/_example/example.html`.

### Система HTML-чанков

В шаблоне работает система чанков на основе пакета `gulp-file-include`, благодаря которому можно разделять HTML-файлы на блоки.  
Все чанки находятся в папке `html/chunks/`. Здесь есть основные стартовые чанки *(head, header, footer, modals и тд)*, которые уже подключены к стартовой странице. Помимо основных чанков, сюда вы можете добавлять свои собственные и вызывать их в любом месте страницы с помощью конструкции `@@include('../chunks/header.html')` (это пример для страницы внутри папки `pages`).  
Также есть возможность передавать параметры внутрь чанков, чтобы переиспользовать их в разных местах или страницах. Вот пример конструкции с передаваемым параметром `title` - `@@include('../chunks/head.html', {title: 'Главная страница'})`, при этом, внутри файла `head.html` должен быть указан параметр `@@title`, на место которого будет вставлен заголовок.  
Это не все возможности пакета `gulp-file-include`, но они наиболее часто используемые, если хотите узнать больше - [вот ссылка на репозиторий](https://github.com/haoxins/gulp-file-include).

### <h3 id="html-a11y">Доступность разметки</h3>
Чанки и сниппеты шаблона уже размечены так, чтобы страницу можно было пройти с клавиатуры и прочитать скринридером. Придерживайтесь тех же правил в своей вёрстке — форк унаследует их во все проекты.

**Кнопке нужен `type`.** По умолчанию `<button>` имеет тип `submit` и внутри формы отправляет её:

	<button type="button" class="modal-link button" data-modal-open="callback">

Исключение — кнопка закрытия внутри `<form method="dialog">`: там нужен именно `submit`, он и закрывает окно.

**Кнопке нужна подпись.** Если внутри только иконка, текста для скринридера нет — добавьте `aria-label`:

	<button type="button" class="notify__close" aria-label="Закрыть" popovertarget="addToCart" popovertargetaction="hide">

**Иконки спрайта прячутся от скринридера.** Они дублируют текст рядом или подпись кнопки, поэтому читать их не нужно. `focusable="false"` убирает иконку из обхода по `Tab`:

	<svg aria-hidden="true" focusable="false" class="icon" width="24" height="24"><use href="img/sprite.svg#close"></use></svg>

Сниппет `svg` вставляет заготовку сразу с этими атрибутами.

**Элемент, который раскрывает что-то, сообщает об этом.** Бургер, кнопка открытия окна и пункт меню с подменю несут `aria-expanded`; шаблон переключает его сам при открытии и закрытии.

**Скрытое должно быть скрыто по-настоящему.** `opacity: 0` и увод за экран оставляют ссылки и кнопки доступными для `Tab` и видимыми для скринридера. Для скрытия используйте `display`, `visibility` или нативные состояния `<dialog>` и `popover` — так сделаны модалки, боковое меню, оповещения, подменю и тултипы. Если элемент нужно спрятать только визуально, оставив его для скринридера, есть класс `sem-hide`.


## Именование классов
Общий подход в организации структуры и именование классов я делаю по БЭМ. Есть некоторые "монолитные классы", которые зафиксированы в каждом проекте и не меняются в связи со своей универсальностью. Также есть некоторые кастомные именования, которые продиктованы логикой шаблона.  

### Базовая структура страницы
Пример базовой структуры страницы, которая кочует от проекта к проекту и не меняется *(как раз тут используются монолитные классы)*:

	<body class="page"> --> для body всегда класс 'page'
		<div class="wrapper"> --> внутри body обертка с классом 'wrapper', всегда ее использую, помогает реализовать неожиданные дизайнерские запросы
			<header class="header"> --> для header всегда класс 'header'
				<div class="header__container container"></div> --> внутри header ограничивающий контейнер с классом 'header__container' и компонентом 'container'
			</header>
			<main class="content"> --> для main всегда класс 'content', на котором завязано многое далее по дереву
				<section class="content__block"> --> каждый уникальный раздел/блок страницы всегда с тегом section и классом-элементом 'content__block'
					<div class="content__container container"> --> внутри раздела/блока всегда ограничивающий контейнер с классом-элементом 'content__container'
						<div class="custom-block"></div> --> тут уже можем встраивать структуру конкретного раздела/блока с уникальными классами
					</div>
				</section>
			</main>
			<footer class="footer"> --> для footer всегда класс 'footer'
				<div class="footer__container container"></div> --> внутри footer ограничивающий контейнер с классом 'footer__container'
			</footer>
		</div>
	</body>

*Раньше я начинал разметку конкретных блоков прямо с тега `section`, типа `.content__block.custom-block ➔ .custom-block__container ➔ .custom-block__body` и тд, но отказался от такого подхода, так как он изначально заставляет вас создавать кучу пустых и не нужных классов. Теперь уникальные блоки начинаются внутри ограничивающего контейнера. А если необходимо изменить к примеру контейнер, можно обратиться к нему через селектор `:has`.*

### Примечания по некоторым монолитным классам
Большинство монолитных классов расположены в файле `src/scss/layout/base.scss`. Обязательно ознакомьтесь с этим файлом, чтобы понимать логику структуры выше.

`[какой-то-блок]__container` — БЭМ-имя ограничивающего контейнера. Само по себе оно ничего не стилизует: ширину, центрирование и боковые отступы задаёт компонент `container`, который ставится рядом.

	<div class="content__container container">

К контейнеру конкретного блока обращайтесь по его БЭМ-имени, например `.header__container`.

Появление при прокрутке — отдельный компонент `appear`, он ставится туда, где анимация нужна:

	<div class="content__container container appear">

Анимация построена на `animation-timeline: view()` и целиком отключается у посетителей с `prefers-reduced-motion: reduce`.

### <h3 id="component-api">Подключение встроенных компонентов (data-атрибуты)</h3>
Встроенные компоненты шаблона подключаются data-атрибутами: `data-tabs`, `data-slider`, `data-modal`, `data-spoiler` и тд.

	<div class="tabs" data-tabs>

Один и тот же атрибут делает две вещи: по нему скрипт находит компонент на странице и по нему же работают технические стили. Классы остаются целиком в вашем распоряжении — они нужны только для оформления и живут по правилам БЭМ. Класс можно переименовать под дизайн: поведение компонента от него не зависит.

#### Как устроен атрибут компонента
Корень компонента — атрибут во множественном числе или по имени компонента, его части — тот же префикс с уточнением:

	<div class="tabs" data-tabs>
		<div class="tabs__link-list">
			<button type="button" class="tabs__link" data-tab-link>Таб 1</button>
		</div>
		<div class="tabs__content-list" data-tab-panels>
			<div class="tabs__content" data-tab-panel>Контент 1</div>
		</div>
	</div>

Режимы работы компонента задаются значением корневого атрибута:

	<div class="tabs" data-tabs="empty">

Значений можно указать несколько через пробел — стили ищут их селектором `[data-tabs~="empty"]`.

Атрибут со значением-идентификатором связывает элементы между собой: `data-modal-open="callback"` открывает окно `<dialog id="callback" data-modal>`, а `data-slider="example"` задаёт имя слайдера, к которому обращаются настройки Swiper.

#### Свои компоненты
Для собственных компонентов проекта используйте такую же схему: атрибут `data-<имя>` для корня, `data-<имя>-<часть>` для частей. Как подключить свой модуль к реестру — в разделе [Реестр модулей и ленивая загрузка](#module-registry).

### <h3 id="component-states">Состояния компонентов</h3>
Состояние — это то, что меняется во время работы страницы: окно открыто, таб выбран, поле заполнено, страница прокручена.

**Сначала берите то, что браузер знает сам.** У нативных элементов состояние уже есть, и его видно в CSS без единой строчки JS:

| Селектор | Состояние |
| :--- | :--- |
| `dialog[open]` | модальное окно открыто |
| `details[open]` | спойлер раскрыт |
| `:popover-open` | оповещение показано |
| `:checked` | чекбокс или радио отмечены |
| `:placeholder-shown` | в поле ничего не введено |
| `:user-valid` / `:user-invalid` | поле прошло или не прошло проверку *(только после ввода)* |
| `:disabled` | элемент выключен |

**Дальше — ARIA.** Когда состояние нужно и стилям, и скринридеру, оно живёт в ARIA-атрибуте, и стили читают тот же атрибут. Так внешний вид и доступность не могут разойтись:

| Атрибут | Где используется в шаблоне |
| :--- | :--- |
| `aria-selected="true"` | активная ссылка табов |
| `aria-expanded="true"` | бургер и пункт меню с раскрытым подменю |
| `aria-current="location"` | пункт оглавления статьи, до которого долистал посетитель |

	.tabs__link[aria-selected="true"] {
		background-color: var(--c-main);
	}

**Всё остальное — в `data-state`.** Значения разделяются пробелом, селектор — `[data-state~="fill"]`:

	<div class="form__field" data-state="fill">
	<body data-state="load-dom load scroll">

	.form__field[data-state~="fill"] {
		border-color: var(--c-main);
	}

Из JS состояние ставится утилитой `setState` — она добавляет и убирает отдельное значение, не затирая остальные:

	import setState from '../utils/setState.js';

	setState(field, 'fill', Boolean(input.value));

Состояния, которые шаблон ставит на `<body>`: `load-dom`, `load` *(модуль [detectPageLoad](#detectPageLoad))*, `scroll` *([detectPageScroll](#detectPageScroll))*, `lock`, `lock-clear` и `lock-<имя окна>` *(модуль [pageLock](#раздел-1-технические-модули))*.

	│   └── ...

### Файлы index.scss
Файл `index.scss` собирает свою папку: он форвардит все `.scss` этой папки, и сама папка подключается одной строкой.

В папках `components/`, `layout/` и `_example/` эти файлы генерируются автоматически задачей `generateIndexSCSS` перед каждой компиляцией стилей — **править их руками не нужно**, они лежат в `.gitignore` и будут перезаписаны. Добавили новый файл в `components/` — он подключится сам. Это касается и вложенных папок: у `components/form/` свой сгенерированный индекс, и любая новая подпапка получит его автоматически.

Файлы форвардятся в алфавитном порядке. Внутри слоя порядок правил зависит от имён файлов, поэтому не стройте каскад на том, что один компонент идёт раньше другого — за приоритет отвечают слои.

В остальных папках *(`abstracts/`, `base/`, `tech/`)* индексы написаны руками: там порядок подключения осмысленный, и новый файл нужно дописать в `index.scss` самому.

### Каскадные слои
Весь CSS шаблона распределён по каскадным слоям (`@layer`). Порядок слоёв объявлен в `src/scss/main.scss` первой строкой и определяет, чей стиль победит:

```scss
@layer base, vendors, tech, example, components, layout, demo;
```

| Слой | Что в нём | Откуда берётся |
| :--- | :--- | :--- |
| `base` | сброс, подключение шрифтов, общие `@keyframes` | `base/` |
| `vendors` | CSS сторонних библиотек (Swiper, PhotoSwipe) | `node_modules` |
| `tech` | техническая механика встроенных компонентов | `tech/` |
| `example` | оформление страниц примеров, собирается в отдельный `example.css` | `_example/` |
| `components` | внешний вид компонентов | `components/` |
| `layout` | блоки страницы: шапка, футер, сетка, контейнеры | `layout/` |
| `demo` | оформление стартовой страницы шаблона | `_demo/` |

Чем ниже слой в списке, тем он сильнее. Правило из `components` перебивает правило из `tech`, даже если селектор в `tech` длиннее — специфичность сравнивается только внутри одного слоя. Поэтому оформление компонента пишется обычными короткими селекторами, без `!important` и без цепочек вроде `.block .block__element.active`.

Стиль вне слоя сильнее любого слоя, поэтому новые файлы стилей подключаются через существующие папки. Если нужен ещё один слой — добавьте его имя в список и подключите содержимое через `meta.load-css`:

```scss
@layer print {
	@include meta.load-css('print');
}
```

`@use` нельзя вложить в `@layer` — Sass требует, чтобы `@use` шёл в начале файла. Поэтому содержимое слоёв подключается миксином `meta.load-css` из `sass:meta`: он вставляет CSS этого модуля прямо в то место, где вызван. На `@use` внутри самих файлов стилей это не влияет — переменные, функции и миксины подключаются как обычно.

### Встроенные компоненты шаблона
В шаблоне есть некоторые готовые компоненты (по типу табов, спойлеров, модалов и тд), в папке `src/scss/components/` находятся заготовки для этих и прочих встроенных компонентов.  
Самые масштабные компоненты описаны в разделе [JS-скрипты](#js-скрипты), чтобы не описывать один компонент два раза, я буду оставлять ссылки на раздел со скриптами для каждого такого случая. Все остальные компоненты будут описаны в текущем разделе.  

Так же для некоторых компонентов существуют технические стили, которые находятся в файлах с аналогичными названиями в директории `src/scss/tech/`. Технические стили - это постоянно необходимые стили для компонентов, которые отвечают за логику *(в то время, как файлы в директории `components` отвечают за внешний вид)*.

Техническим стилям соответствует слой `tech`, оформлению — слой `components`, и `components` всегда сильнее. Поэтому переопределить механику можно обычным коротким селектором, без `!important` и без длинных цепочек — подробнее в разделе [Каскадные слои](#каскадные-слои). Селекторы технических стилей построены на data-атрибутах компонента *(`[data-tabs]`, `[data-modal]`)*, а классы отданы оформлению — см. [Подключение встроенных компонентов](#component-api).

#### Настройки технических стилей
Часто меняющиеся величины вынесены из технических стилей в CSS-переменные со значением по умолчанию. Чтобы поменять их, объявите переменную в стилях своего компонента:

```scss
.modal {
	--modal-duration: 0.2s;
}
```

| Переменная | Что задаёт | По умолчанию |
| :--- | :--- | :--- |
| `--modal-duration` | длительность появления модального окна | `$td` |
| `--hide-menu-duration` | длительность выезда бокового меню | `0.8s` |
| `--burger-duration` | длительность анимации иконки бургера | `0.8s` |
| `--notify-duration` | длительность появления оповещения | `$td` |
| `--notify-offset` | отступ оповещения от края экрана | `1rem`, на мобильных `0` |
| `--tabs-duration` | длительность переключения табов | `$td` |
| `--spoiler-duration` | длительность раскрытия спойлера | `$td` |
| `--tooltip-duration` | длительность появления тултипа | `$td` |
| `--navigation-duration` | длительность раскрытия подменю | `$td` |

`$td` — общее для сайта значение `transition-duration` из `src/scss/abstracts/variables.scss`.  

#### Глоссарий
**Компонент-модификатор** – это компонент, к которому не привязан JS-скрипт. Достаточно лишь указан соответствующий класс.  
**Компонент-модуль** – это компонент, к которому привязан JS-скрипт. Подробнее о каждом такому модуле по ссылке, либо в разделе [JS-скрипты](#js-скрипты).  
**Компонент-блок** – это компонент, к которому не привязан JS-скрипт, но для его работы необходимо использовать HTML-конструкцию *(вызов каждой конструкции осуществляется через сниппет)*.

#### container. Компонент-модификатор
Ограничивает ширину содержимого, центрирует его и задаёт боковые отступы страницы. Ставится рядом с БЭМ-именем контейнера: `<div class="content__container container">`. Максимальную ширину и отступы задают переменные `$maxWidthContainer` и `$containerMargin` в `src/scss/abstracts/variables.scss`. Модификатор `container--wide` расширяет контейнер до 2560px.
#### appear. Компонент-модификатор
Появление элемента при прокрутке: блок выезжает снизу и проявляется по мере входа в окно просмотра. Работает на `animation-timeline: view()`. У посетителей с `prefers-reduced-motion: reduce` анимация не подключается. Кадры анимации лежат в `src/scss/base/timeline.scss`.
#### sans-serif. Компонент-модификатор
Требуется для обрамления alt-символов, если шрифт проекта не поддерживает нормальное их отображение, либо оно не соответствует ожиданиям. Примеры таких символов: ✓ © ♫ →
#### ruble. Компонент-модификатор
Требуется для обрамления символа рубля (₽), если шрифт проекта не поддерживает его нормальное отображение.

#### <h4 id="navigation-component">navigation. Компонент-блок</h4>
Меню сайта с выпадающими подменю любой вложенности. Разметка — в чанке `src/html/chunks/navigation.html`, механика раскрытия — в `src/scss/tech/navigation.scss`, оформление — в `src/scss/layout/navigation.scss`. Закрытие по `Esc` и по клику вне меню — модуль [initNavigation](#initNavigation). Пример — на странице `src/html/_example/example-navigation.html`. Корневому `<nav>` нужен атрибут `data-navigation`, по нему модуль подгружается.

Пункт, который раскрывает подменю, размечается тегом `<button>`: фокус на нём открывает подменю с клавиатуры.

	<li class="navigation__list-item">
		<button type="button" class="navigation__list-link">Выпадающее меню</button>
		<svg class="navigation__level-icon icon" width="16" height="16" aria-hidden="true" focusable="false"><use href="img/sprite.svg#chevron"></use></svg>
		<div class="navigation__level-container">
			<ul class="navigation__level-list">…</ul>
		</div>
	</li>

Подменю раскрывается двумя способами: наведением — только там, где указатель это умеет *(`@media (hover: hover)`)*, и фокусом внутри пункта *(`:focus-within`)*. Второе покрывает клавиатуру и сенсорные экраны: тап по кнопке ставит на неё фокус и открывает подменю, тап мимо — закрывает.

Закрытое подменю скрыто через `visibility: hidden`, поэтому ссылки внутри него не ловят `Tab` и не читаются скринридером. Меняя анимацию раскрытия, оставьте `visibility` в переходе.

Вложенное подменю *(третий уровень)* размечается так же, но контейнеру добавляется модификатор `navigation__level-container--inside` — он разворачивает подменю вбок.

### Использование переменных, функций и миксинов

#### Вызов цветов
Цвета прописываются в файл `src/scss/base/colors.scss` как CSS-переменные на `:root`, там уже есть примеры цветов.  
Перед каждым цветом нужно выставить префикс `--c-`, чтобы его можно было быстро найти через сниппет. Сниппет для быстрой вставки цвета - `vc`, он вставляет `var(--c-…)`.

```scss
:root {
	color-scheme: light dark;

	--c-main: light-dark(#1D201F, #F7F9F7);
	--c-accent: light-dark(#F7F9F7, #1D201F);
	--c-brand: #45C95A;
}
```

`light-dark()` принимает два значения: первое для светлой схемы, второе для тёмной. Цвет, одинаковый в обеих схемах, пишется обычным значением — как `--c-brand` выше. Какая схема активна, решает свойство `color-scheme`, подробнее — в разделе [Темизация и работа с темами](#темизация-и-работа-с-темами).

**Прозрачность** задаётся через `color-mix`, функция `rgba()` с CSS-переменной не работает:

```scss
background-color: color-mix(in srgb, var(--c-main) 20%, transparent);
```

Так же через `color-mix` смешиваются два цвета палитры — это удобно для промежуточных оттенков, чтобы не заводить под них отдельную переменную:

```scss
color: color-mix(in srgb, var(--c-main) 60%, var(--c-accent) 40%);
```

CSS-переменные не читаются в медиа-запросах (`@media (min-width: var(--x))` не работает), поэтому размеры и брейкпоинты живут в Sass-переменных `src/scss/abstracts/variables.scss`.

#### Вызов стилей шрифтов
Стили шрифтов прописываются через миксины в файле `src/scss/abstracts/font-styles.scss`, там уже есть примеры стилей шрифтов.  
Перед каждым миксином нужно выставить префикс `f-`, чтобы его можно было быстро найти через сниппет. Сниппет для быстрой вставки миксина шрифта - `f`.

#### Вызов эффектов

### Адаптивное свойство (lineScale-миксин)
Про миксин lineScale расскажу подробнее. Это так называемое адаптивное свойство. Пример: вы назначаете блоку первоначальную ширину `500px`, а конечную `200px`, при уменьшении экрана от `1440px` до `480px` размер блока будет пропорционально уменьшаться в заданном вами промежутке размера *(500px->200px)*, промежуток экрана так же можно изменять. Можно назначать это свойство для любых элементов *(блоки, шрифты и тд)*. Больше информации о логике работы адаптивного свойства можно найти в интернете.  
Я взял самый распространенный Sass-миксин для реализации этого функционала и доработал его под нужды шаблона. Что было улучшено:
- изменил порядок назначения промежутков размера *(от большего к меньшему);*
- добавил возможность увеличивать блок, а не только уменьшать;
- добавил возможность использовать отрицательные единицы.

#### Пример использования
Сниппет для быстрой вставки lineScale-миксина - `ls`. Миксин после вставки выглядит вот так - `lineScale(,,480,1440)`.  
Разберем, что означает каждый аргумент в этом примере: `lineScale([1],[2],[3],[4])`  
> Все значения указываем в пикселях без единицы измерения *(в конечном итоге они будут автоматически преобразованы в `rem`)*.  
1. Первоначальный размер элемента - `lineScale(500,[2],[3],[4])`
2. Конечный размер элемента - `lineScale(500,200,[3],[4])`
3. До какого размера экрана будет изменяться элемент - `lineScale(500,200,768,[4])`
4. От какого размера экрана будет изменяться элемент - `lineScale(500,200,768,992)`  

**Итого, мы имеем следующее** - размер элемента будет пропорционально уменьшаться от `500px` до `200px` при изменении размера экрана от `992px` до `768px`.

Для визуального облегчения кода можно использовать lineScale-миксин без указания размеров экрана - `lineScale(500,200)`.  
В таком случае они будут заданы по-умолчанию от `1440px` до `480px`.

Пример отрицательного изменения *(пригодится при работе со свойством translate)* - `lineScale(100,-50)`  
Пример обратного изменения *(от меньшего к большему)* - `lineScale(200,500)`

### Систематизация `z-index`

Чтобы на протяжении всей жизни проекта контролировать приоритет наложения блоков и компонентов *(блокировку страницы, модальные окна, всплывающие подсказки и прочие подобные блоки)*, в шаблоне предусмотрена систематизация значений `z-index`.

#### Границы использования:

Верхний порог значений - `z-index: 10`  
Нижний порог значений - `z-index: -1`

#### Правила использования:

| Категория | Значение |
| ------ | ------ |
| Модальные окна | `z-index: 10` |
| Боковое меню | `z-index: 8` |
| Page-lock | `z-index: 6` |
| Фиксированная шапка | `z-index: 4` |
| Оповещения(notify) | `z-index: 4` |

**Важное примечание:** `z-index` для модальных окон и бокового меню учитывается только в том случае, если вы по какой-то неведомой причине решите отказаться от их работы на `dialog` тегах, так как они и так всегда буду выше всего на странице *(и на это пока никак нельзя повлиять)*.

*Все стандартные значения уже заданы в технических стилях стандартных блоков/компонентов;*  
*Промежутки между значениями можно использовать для кастомных блоков/компонентов.*  

### Темизация и работа с темами
Тема переключается свойством `color-scheme`, а значения цветов под каждую схему задаёт `light-dark()` в `src/scss/base/colors.scss`. Отдельного набора переменных на тёмную тему нет — цвет описан один раз в двух вариантах.

По умолчанию `:root` объявлен как `color-scheme: light dark` — сайт следует системной настройке посетителя. Вместе с цветами под схему подстраиваются и элементы, которые рисует браузер: полосы прокрутки, чекбоксы, календарь в `input[type="date"]`.

Ручное переключение — атрибут `data-theme` на `<html>`:

```html
<html data-theme="dark">
```

| Значение | Поведение |
| :--- | :--- |
| атрибута нет | тема следует за системной настройкой |
| `data-theme="light"` | всегда светлая |
| `data-theme="dark"` | всегда тёмная |

Выбор посетителя применяется до первой отрисовки страницы, поэтому переключатель состоит из двух частей — инлайн-скрипта в `<head>` и обработчика кнопки:

```html
<script>
	const theme = localStorage.getItem('theme');
	if (theme) document.documentElement.dataset.theme = theme;
</script>
```

```js
const setTheme = (theme) => {
	document.documentElement.dataset.theme = theme;
	localStorage.setItem('theme', theme);
};
```

Скрипт в `<head>` подключается инлайном и без `defer` — так он выполняется до первой отрисовки.

Тёмная тема — это не инверсия светлой. Тени на тёмном фоне почти не видны, поэтому вместо них обычно берут подсветку границы; крупные заливки фирменным цветом на тёмном выглядят ярче и часто требуют приглушения. Проверяйте обе схемы: в DevTools это *Rendering → Emulate CSS media feature prefers-color-scheme*.

### <h3 id="module-contract">Контракт модулей</h3>

Все модули шаблона устроены одинаково, и от этого зависит, как их подключать и переиспользовать.

**Каждый модуль экспортирует функцию `init(root = document)`.** Она ищет свою разметку внутри `root` и навешивает обработчики. Никаких действий при импорте модуль не выполняет.

**Модуль молча выходит, если его разметки нет.** Сообщение в консоль он пишет только тогда, когда разметка есть, но она неполная *(например, у спойлера нет содержимого)* — и только в dev-сборке, в продакшн-бандл эти сообщения не попадают.

**Повторный вызов безопасен.** Модуль помечает уже обработанные узлы, поэтому второй вызов не навесит вторую пару обработчиков. Благодаря этому подгруженный аяксом фрагмент инициализируется одной строкой:

```js
import { initModules } from './modules/index.js';

// после вставки фрагмента в DOM
initModules(fragment);
```

##### ❗️ПРИМЕЧАНИЕ
Если пишете свой модуль — придерживайтесь того же контракта: экспортируйте `init(root)`, выходите при отсутствии разметки и оборачивайте поиск элементов в утилиту `initOnce` из `modules/utils/`. Тогда модуль попадёт в общий реестр и будет работать с аякс-подгрузкой наравне с остальными.

### <h3 id="module-registry">Реестр модулей и ленивая загрузка</h3>

Файл `js/modules/index.js` — это список пар «селектор разметки → модуль»:

```js
const LAZY_MODULES = [
	['[data-tabs]', () => import('./func/initTabs.js')],
	['[data-slider]', () => import('./lib-control/sliders.js')],
];
```

Модуль скачивается и запускается, **только если его разметка есть на странице**. На странице без слайдера не загрузится Swiper, без маски телефона — IMask, а ядро галереи подтянется лишь в момент открытия изображения. Поэтому лишние модули не нужно отключать вручную: они ничего не стоят до тех пор, пока не появится разметка.

Из-за этого `main.js` весит около 2 КБ, а всё остальное лежит отдельными файлами в `build/js/chunks/` и подгружается по мере надобности.

##### ⚙️НАСТРОЙКИ
- Выключить модуль совсем — закомментировать его строку в `LAZY_MODULES`;
- Добавить свой модуль — дописать пару «селектор → импорт» туда же;
- Модуль, которому не нужна разметка *(детекторы, замеры)*, добавляется в массив `ALWAYS` выше.

### Сборка JS
Скрипты собираются [esbuild](https://esbuild.github.io/) из `src/js/main.js` в `build/js/main.js`: все импорты объединяются в один файл, в продакшн-сборке он минифицируется, в dev рядом создаётся карта кода `main.js.map`. Версии синтаксиса подбираются по `browserslist` из `package.json`.
> - Бандл собирается в формате ES-модуля и подключается как `<script type="module" src="js/main.js"></script>` *(чанк `scripts.html`)*. Модульный скрипт выполняется после разбора HTML, как обычный скрипт в конце `body`;
> - Включено разбиение на чанки: если подключить модуль динамически *(`import('./modules/lib-control/sliders.js')`)*, он соберётся в отдельный файл `build/js/chunks/` и загрузится только при вызове;
> - Модульные скрипты не работают при открытии HTML-файла напрямую с диска *(`file://`)* — страницы из `build` нужно открывать через сервер: `pnpm dev`, тестовый хостинг или любой локальный сервер.

### Раздел 1. Технические модули
От этих скриптов зависит работа некоторых функциональных модулей, так что без особой необходимости нет смысла к ним обращаться.  

У технических модулей нет основного файла, так как они вызываются по необходимости внутри функциональных модулей, путь до технических модулей - `js/modules/tech/`.  

#### Модуль 1.1. Блокировка страницы (pageLock)
Содержит функцию для блокировки страницы при вызове выезжающего меню, попапов и тд.  
Блокируется скролл и взаимодействие с любыми элементами страницы, кроме активного.  
При вызове можно добавить кастомный класс.  
Вызов `pageLock('lock', base, name)` дописывает в `body[data-state]` значение `lock` *(и `lock-name`, а при `base === false` — `lock-clear`)*, вызов `pageLock('unlock')` убирает только значения `lock` и `lock-*`, остальные состояния `body` не затрагиваются.

#### <h4 id="getBlockHeight">Модуль 2.1. Получение высоты блоков (getBlockHeight)</h4>
Данный модуль вычисляет высоту блока по его максимальному значению.  

Чтобы вычислить высоту блока, необходимо назначить ему атрибут `data-get-height`. В этом случае высота блока будет через инлайн-стили записана на ближайший блок с классом `content__block` в переменную `--target-height` в rem единицах.  

##### ⚙️НАСТРОЙКИ
Если вам нужно записать значение высоты на определенный блок, то этому блоку задаём атрибут `data-height-goal`.

##### ❗️ПРИМЕЧАНИЕ
Модуль рассчитан на работу только с одним вычисляемым блоком внутри одного контейнера.

#### <h4 id="initTabs">Модуль 2.2. Табы (initTabs)</h4>

Табы - это несколько ссылок и такое же кол-во привязанных к ним табов *(блоков)*. При нажатии на определенную ссылку открывается привязанный к ней таб, а предыдущий открытый таб пропадает, что позволяет переключаться между табами на странице, выводя разную информацию в одном месте.  

**Примечания по обозначениям:**  
**Контейнер** - это блок, внутри которого расположены ссылки и табы;  
**Ссылка** - это якоря табов, при клике на каждый из которых будет показан свой таб;  
**Контейнер табов** - это блок, внутри которого расположены табы;  
**Таб** - это тело одного таба, в котором будет ваша информация.  

**Ссылки** и **табы** должны быть расположены внутри одного основного **контейнера**.  
Для каждой отдельной группы **табов** свой **контейнер**.  
- указываем атрибут `data-tabs` для основного **контейнера**;
- указываем атрибут `data-tab-link` для **ссылок**;
- указываем атрибут `data-tab-panels` для **контейнера** **табов**;
- указываем атрибут `data-tab-panel` для **табов**;
- указываем `aria-selected="true"` одной **ссылке** и `data-state="active"` одному **табу** *(обычно это первая ссылка и первый таб)*, которые будут показаны изначально *(после загрузки страницы)*;  

**Ссылок** и **табов** должно быть одинаковое количество *(спасибо, кэп)*.  
Внутри основного **контейнера** могут располагаться блоки любой вложенности.  

##### ⚙️НАСТРОЙКИ
Изначально табы работают с `fade-эффектом` *(плавно исчезает текущий и плавно появляется выбранный таб)*, так же плавно подстраивается по высоте контейнер табов.  
Чтобы изменить это поведение, есть пара модификаторов:  
- Указываем `data-tabs="slide"` основному контейнеру, чтобы переключить режим анимации в `slide-эффект` *(табы будут замещать друг-друга с плавным изменением высоты)*;
- Указываем `data-tabs="noanim"` основному контейнеру, чтобы отключить любую анимацию переключения табов;
- Указываем `data-tabs="empty"` основному контейнеру, чтобы включить `пустой режим`. В этом режиме при повторном нажатии ссылки, привязанный к этой ссылке таб будет сворачиваться *(в обычном режиме - его нельзя свернуть)*. *Примечание: этот режим можно использовать для сворачивания какого-либо блока по клику на ссылку*. *Примечание 2: в этом режиме поведение табов будет как в режиме `data-tabs="slide"`*;  

Глобально настроить скорость анимации и саму анимацию можно в файле `tabs.scss`, так же вы можете настроить анимацию конкретных табов, через уникальные классы вашего блока с табами.

##### 👀ПРИМЕРЫ
Стандартную структуру одного блока с табами можно вызвать сниппетом `cmp|tab`.

Пример основного контейнера:

	<div class="tabs-block" data-tabs>
		<div class="tabs-block__link-list">
			<button type="button" class="tabs-block__link" data-tab-link aria-selected="true">Ссылка таба 1 (Будет активна изначально)</button>
			<button type="button" class="tabs-block__link" data-tab-link>Ссылка таба 2</button>
			<button type="button" class="tabs-block__link" data-tab-link>Ссылка таба 3</button>
		</div>
		<div class="tabs-block__content-list" data-tab-panels>
			<div class="tabs-block__content" data-tab-panel data-state="active">
				<h1>Контент таба 1 (Будет активен изначально)</h1>
			</div>
			<div class="tabs-block__content" data-tab-panel>
				<h1>Контент таба 2</h1>
			</div>
			<div class="tabs-block__content" data-tab-panel>
				<h1>Контент таба 3</h1>
			</div>
		</div>
	</div>
	*Следующие блоки с табами должны иметь свой data-tabs (свой контейнер)

#### <h4 id="initSliders">Модуль 2.3. Слайдер (initSliders)</h4>
В работе слайдера за основу взята библиотека `swiper.js`.  
Я упростил инициализацию и добавил несколько наиболее часто используемых настроек.  
Чтобы инициализировать слайдер, добавляем к блоку-родителю *(в котором будут находится непосредственно слайды. Далее - родитель)* атрибут `data-slider` со значением-именем слайдера.  
Для каждого слайда добавляем атрибут `data-slide`.  
Благодаря предыдущему действию мы можем добавить стрелки управления, пагинацию и прочие элементы `swiper.js` непосредственно в родителя слайдера. Их расположение внутри родителя не имеет значения.  
И затем инициализировать слайдер по этому имени в файле `src/js/modules/lib-control/sliders.js`: `new Swiper('[data-slider="имя"]', { … })`.  
Пример js-инициализации с разобранными параметрами лежит в `src/js/_example/slider.js`. Там же есть предустановленные настройки для таких модулей как навигация, пагинация и скроллбар, которые нужно использовать для правильной работы предустановленных мной стилей этих модулей.  
Пример блока со слайдером — на странице `src/html/_example/example-slider.html`.  
Информацию по прочим параметрам можно найти на <a href="https://swiperjs.com/swiper-api#parameters" target="_blank">сайте библиотеки</a>.

#### <h4 id="spoilers">Модуль 2.5. Спойлеры (нативные, без JS)</h4>
Спойлеры *(или аккордеон)* - это один или несколько раскрывающихся элементов. Как пример: часто их работу можно увидеть в блоке FAQ.  
Спойлеры собираются на нативном теге `<details>` и **не требуют JS вообще**: открытие, закрытие, клавиатура и чтение скринридером работают силами браузера.

Структура такая:
- сам спойлер — тег `<details>` с атрибутом `data-spoiler`;
- заголовок — тег `<summary>` с атрибутом `data-spoiler-title` *(всегда первый элемент внутри `<details>`)*;
- содержимое — **один** блок с атрибутом `data-spoiler-content`, внутри которого уже может лежать что угодно.

Чтобы спойлер был открыт изначально, добавьте ему атрибут `open`.

##### ⚙️НАСТРОЙКИ
- **Одиночный режим *(аккордеон)*.** Задайте всем `<details>` группы одинаковый атрибут `name`: браузер сам закроет предыдущий спойлер при открытии следующего;
- **Скорость анимации** берётся из переменной `$td` *(`abstracts/variables.scss`)*, как и у остальных компонентов шаблона;
- **Стрелка** рисуется в `components/spoiler-list.scss` псевдоэлементом `&__title::after` и поворачивается по `[open]`. Нативный треугольник браузера скрыт в технических стилях, так что иконку можно заменить на любую другую из спрайта.

##### ❗️ПРИМЕЧАНИЕ
Анимация раскрытия сделана на псевдоэлементе `::details-content` через `grid-template-rows: 0fr → 1fr`, поэтому высоту содержимого не нужно замерять скриптом — она всегда корректна, в том числе после переноса строк на узком экране и после загрузки картинок.

В браузерах, которые не знают `::details-content` *(Safari младше 18.4, Firefox младше 143)*, спойлер открывается мгновенно, без анимации — вся остальная механика работает.

##### 👀ПРИМЕРЫ
Пример группы спойлеров в режиме аккордеона:

	<div class="spoiler-list">
		<details class="spoiler-list__item" data-spoiler name="faq" open>
			<summary class="spoiler-list__title" data-spoiler-title>Заголовок спойлера</summary>
			<div class="spoiler-list__content" data-spoiler-content>
				<p>Контент спойлера</p>
			</div>
		</details>
		<details class="spoiler-list__item" data-spoiler name="faq">
			<summary class="spoiler-list__title" data-spoiler-title>Заголовок следующего спойлера</summary>
			<div class="spoiler-list__content" data-spoiler-content>
				<p>Контент следующего спойлера</p>
			</div>
		</details>
	</div>
	*Следующей группе спойлеров на странице задайте другое значение name, иначе группы будут закрывать друг друга

Пример независимых спойлеров *(открываются и закрываются сами по себе)* — то же самое, но без атрибута `name`.

#### <h4 id="anchors">Модуль 2.6. Скролл до якоря (нативный, без JS)</h4>
Обычная ссылка-якорь `<a href="#block">` прокручивает страницу плавно и останавливается под липкой шапкой — своя реализация для этого не нужна.

Отвечают за это две строки в `base/null.scss`: `scroll-behavior: smooth` *(внутри `@media (prefers-reduced-motion: no-preference)`)* и `scroll-padding-top: var(--header-height)`, где высоту шапки держит модуль [calcHeaderHeight](#calcHeaderHeight).

##### ⚙️НАСТРОЙКИ
Если для конкретной цели нужен другой отступ — задайте ей `scroll-margin-top` в стилях компонента, он складывается с общим `scroll-padding-top`.

#### <h4 id="initModals">Модуль 2.7. Модальные окна (initModals)</h4>
Модальное окно - это небольшое *(или большое)* всплывающее окошко, которое появляется на странице, при клике на определенные элементы *(как правило - кнопку)*.  
Тут реализовано простое открытие модальных окон на базе тега `<dialog>`, которое можно модернизировать по своему усмотрению *(добавлять анимации, менять поведение и тд)*.  
Вызов модальных окон осуществляется нажатием на элемент-ссылку.  
Закрытие модальных окон осуществляется нажатием на иконку закрытия, на область вне модального окна, по нажатию клавиши `Esc`, а так же нажатию браузерной клавиши "Вернуться назад" или при соответствующем жесте на мобильном устройстве.  
При открытии окна в историю браузера добавляется запись с хэшем `#id` окна, поэтому кнопка или жест "Назад" закрывает окно, а не уводит со страницы. При закрытии любым другим способом эта запись убирается, дублей в истории не остаётся.  
Чтобы создать элемент-ссылку, необходимо задать для тега `<button>` атрибут `data-modal`, которому необходимо назначить идентификатор (`id`) вызываемого модального окна.  
Само модальное окно создается через тег `<dialog>`, которому необходимо присвоить атрибут `id` со значением идентификатора модального окна и атрибут `data-modal` *(пример модального окна — на странице `src/html/_example/example-modal.html`)*.  
Для контентной части модального окна указываем атрибут `data-modal-content` *(это необходимо для работы прокрутки на мобильных устройствах)*.  

##### ⚙️НАСТРОЙКИ
Появление и скрытие анимируются в `src/scss/tech/modal.scss`. Закрытое окно получает от браузера `display: none`, поэтому переход строится на дискретных свойствах:

```scss
transition:
	opacity $td $tf,
	display $td allow-discrete,
	overlay $td allow-discrete;
```

`display` и `overlay` переключаются скачком, а `allow-discrete` откладывает этот скачок до конца перехода. `overlay` отвечает за пребывание окна в top layer, куда его поднимает `showModal()`. Начальное состояние появления задаёт `@starting-style` внутри `&[open]`.

Чтобы поменять анимацию, замените `opacity` на нужное свойство в обоих местах — в `transition` и в `@starting-style`. Скрытие анимируется, только пока `display` и `overlay` остаются в переходе.

Такой же приём используют боковое меню (`tech/hide-menu.scss`) и оповещения (`tech/notify.scss`).

##### 👀ПРИМЕРЫ
Пример кнопки, для открытия модального окна:

	<button data-modal-open="callback">

Пример самого модального окна — на странице `src/html/_example/example-modal.html`.

#### <h4 id="initArticleLogic">Модуль 2.8. Генерация оглавления (initArticleLogic)</h4>
Данный скрипт отвечает за генерацию оглавления для текстовых блоков.  
Требуется для всякого рода статей и блогов, чтобы сгенерировать оглавление с якорными ссылками *(далее - ссылки)* на разделы текста.  
Чтобы сгенерировать ссылки для оглавления, необходимо создать элемент-пример ссылки и задать ему атрибут `data-article-link`. По подобию этого примера будут сгенерированы все ссылки оглавления.  
Чтобы отметить область контента статьи, необходимо задать для контейнера контента атрибут `data-article`. Внутри данного контейнера будут выбраны все теги `h2` *(далее - цели)* и на них будут сгенерированы ссылки в оглавлении.  
После генерации ссылок, внутри тега ссылки будет расположено содержимое цели, а в атрибуте `href` - ссылка на цель.  
**Идентификаторы целей.** Если у заголовка уже есть `id`, скрипт его сохраняет — внешние ссылки на раздел продолжат работать. Если `id` нет, он собирается из текста заголовка в транслите *(«Заголовок 1» → `zagolovok-1`)*: такие ссылки читаемы и переживают перестановку разделов, в отличие от порядковых номеров.  
**Важно.** Скрипт заточен под списки `ul>li>a` *(для соблюдения семантики)*. Это значит, что атрибут `data-article-link` должен находиться на теге `<li>`, внутри которого уже будет тег `<a>`, которому и будет назначен атрибут `href` *(смотреть **пример ссылки**)*.

##### ⚙️НАСТРОЙКИ
Идентификатор целей *(по-умолчанию - `h2`)* можно сменить в файле модуля `src/js/modules/func/initArticleLogic.js` *(там будет пометка в виде комментария)*

##### ❗️ПРИМЕЧАНИЕ
Скрипт так же добавляет целям атрибут `data-article-target`.  
Данный атрибут нужен для работы `скрипта 2.9`.  
На одной странице может быть несколько статей: заготовка ссылки ищется рядом с её собственным контейнером `data-article`, поэтому блоки не мешают друг другу.

##### 👀ПРИМЕРЫ
Пример ссылки:

	<ul class="article__list">
		<li class="article__list-item" data-article-link><a class="article__list-link">Ссылка-пример для оглавления</a></li>
		// тут будут сгенерированы остальные ссылки, а ссылка-пример удалиться.
		// вот пример уже сгенерированных ссылок:
		<li class="article__list-item" data-article-link><a href="#zagolovok-1" class="article__link">Заголовок 1</a></li>
		<li class="article__list-item" data-article-link><a href="#zagolovok-2" class="article__link">Заголовок 2</a></li>
	</ul>
Пример контента статьи:

	<div class="article__content" data-article>
		<h2>Заголовок 1</h2>
		<p>Lorem ipsum dolor sit amet, consectetur adipisicing elit. Sint commodi provident, explicabo vel corporis itaque fuga repellat at, eius minima qui tempora, a amet doloribus cupiditate ipsam voluptate veritatis modi.</p>
		<h2>Заголовок 2</h2>

#### <h4 id="initArticleLogic">Модуль 2.9. Отслеживание оглавления (initArticleLogic)</h4>
Иногда нужно добавить отслеживание оглавления *(когда юзер долистал до определенного заголовка в статье, то ссылка на этот заголовок в оглавлении подсвечивается)*.  
Хороший пример - когда оглавление и статья расположены в row flex-контейнере и оглавление имеет position: sticky свойство. То есть, оглавление следует за скроллом и всегда видно, где сейчас находится юзер.  
Данный скрипт работает в автоматическом режиме и не требует каких-либо манипуляций с html-структурой.  
Ссылка, до заголовка которой долистал юзер, получает атрибут `aria-current="location"`. Если в зоне видимости появляется другой заголовок, атрибут у предыдущей ссылки пропадает.  
Отслеживание построено на `IntersectionObserver`.

#### <h4 id="initNotify">Модуль 2.10. Оповещения (initNotify)</h4>
Оповещения - это небольшие окошки, которые будут оповещать пользователя о тех иных действиях, которые он делает.  
Работают они на новых `popover` элементах. Что делает их максимально производиетльными.  
Вызов оповещения осуществляется нажатием на элемент-ссылку.  
Закрытие оповещений осуществляется нажатием на иконку закрытия, на область вне оповещения, по нажатию клавиши `Esc`, а так же по прошествии заданного количества времени.  
Чтобы создать элемент-ссылку, необходимо задать для любого тега атрибут `popovertarget`, которому необходимо назначить идентификатор вызываемого оповещения.  
Так же желательно назначить атрибут `popovertargetaction`, со значением `show` *(подробнее обо всех возможностях `popover` можно прочитать например <a href="https://doka.guide/html/popover/" target="_blank">тут</a>)*.  
Само оповещение создается через добавление к любому блоку атрибута `popover` и атрибута `id`, со значением идентификатора оповещения *(примеры оповещений — на странице `src/html/_example/example-notify.html`)*. Так же необходимо задать атрибут `data-notify`.

##### ⚙️НАСТРОЙКИ
Если вам необходимо показывать оповещение сразу после загрузки страницы, необходимо добавить класс `open` к блоку-оповещению, а к атрибуту `popover` добавить значение `manual`.  
Например, это необходимо для окошка с cookie-оповещением *(см. [Модуль 2.11](#initCookie))*.  

Так же можно задать время, через которое будет закрыто оповещение.  
Чтобы это сделать, необходимо добавить к блоку-оповещению data-атрибут `data-popover-time` со значением времени в секундах.  
Если не задавать атрибуту значение, то будет применено стандартное в 3 секунды.

##### 👀ПРИМЕРЫ
Пример элемента, для показа оповещения:

	<button popovertarget="addToCart" popovertargetaction="show">Добавить в корзину</button>

Примеры самих оповещений — на странице `src/html/_example/example-notify.html`.

#### <h4 id="detectPageLoad">Модуль 2.15. Детектор загрузки страницы (detectPageLoad)</h4>

**Важно!** Не рекомендуется использовать это для анимации блоков при загрузке страницы, так как если скрипты js не загрузятся или произойдет сбой, то пользователь не увидит контент, который будет скрыт стилями.

#### <h4 id="detectPageScroll">Модуль 2.16. Детектор прокрутки страницы (detectPageScroll)</h4>
Дописывает в `body[data-state]` значение `scroll`, когда страница прокручена на `100px`, и убирает его, когда прокрутка меньше `100px`.

#### <h4 id="tooltips">Модуль 2.17. Тултипы (нативные, без JS)</h4>
Тултипы - это небольшие всплывающие окошки, в которых, как правило, находится какая-то справочная информация.  
Тултип работает на чистом CSS и не требует скрипта.

Чтобы создать тултип, задайте блоку-контейнеру атрибут `data-tooltip`, а внутри создайте два элемента: кнопку с атрибутом `data-tooltip-button` и тело подсказки с атрибутом `data-tooltip-body`. Внутрь тела вставляется текст *(или любой другой контент)*, внутрь кнопки — информационная иконка.

**Кнопка должна быть тегом `<button type="button">`**, а не `<span>` или `<div>`. Именно от этого зависит доступность: тултип открывается не только по наведению мыши, но и по фокусу — с клавиатуры *(Tab)* и по тапу на сенсорном экране, где наведения не существует в принципе.

##### ⚙️НАСТРОЙКИ
Технические стили лежат в `tech/tooltip.scss`: открытие по `:hover` обёрнуто в `@media (hover: hover)`, чтобы на сенсорных экранах подсказка не «залипала», а `:focus-within` работает везде. Оформление *(фон, отступы, положение)* — в `components/tooltip.scss`, пример оформления — в `_example/tooltip.scss`.

##### ❗️ПРИМЕЧАНИЕ
Заготовку тултипа можно вставить сниппетом `cmp|tooltip`.

##### 👀ПРИМЕРЫ
Пример тултипа — на странице `src/html/_example/example-tooltip.html`.

#### <h4 id="initNavigation">Модуль 2.18. Закрытие выпадающего меню (initNavigation)</h4>
Подменю в [навигации](#navigation-component) раскрывается на чистом CSS через `:focus-within`, а этот псевдокласс не различает, как элемент получил фокус — по клику мышью или по `Tab`. Из-за этого клик мышью по пункту с подменю ведёт себя как переход табом: фокус остаётся на кнопке, и подменю не закрывается, пока фокус не уйдёт. Модуль добавляет два способа закрыть меню, которых чистому CSS не хватает.

- **`Esc`** — если фокус внутри верхнего пункта меню, но не на его собственной кнопке, первое нажатие возвращает фокус на кнопку и сворачивает вложенные подменю; повторное нажатие снимает фокус целиком и закрывает меню.
- **Клик вне меню** — если открыт какой-то пункт, а клик пришёлся мимо него, фокус снимается явно, не полагаясь на то, что браузер сам уберёт фокус с кнопки.

Модуль ничего не ищет по разметке конкретного `<nav>` — оба слушателя вешаются на `document` один раз и работают для любого числа меню на странице.

##### ⚙️НАСТРОЙКИ
Модуль подключается по атрибуту `data-navigation` на корневом `<nav>` — без него модуль не загрузится, а мышь и тач продолжат открывать меню как обычно.

## Работа с изображениями и иконками

### Оптимизация изображений
Все файлы из `src/img` *(кроме иконок спрайта в `src/img/icons`)* копируются в `build/img` с сохранением структуры папок. В режиме разработки файлы копируются как есть, а удалённые из `src/img` файлы удаляются и из `build/img`.  
В продакшн-сборке изображения сжимаются:
- JPG — mozjpeg, качество 80, прогрессивная загрузка;
- PNG — optipng;
- GIF — gifsicle;
- SVG — svgo с настройками по умолчанию, но `viewBox` сохраняется, чтобы SVG масштабировались через CSS.

Остальные форматы *(WebP, AVIF, ICO, видео и тд)* копируются без обработки — готовьте их уже оптимизированными.  
Настройки сжатия находятся в `gulp/tasks/img.js`.

### <h3 id="svg-generation">Генерация SVG-спрайта (работа с иконками)</h3>
Иконки в шаблоне реализованы через svg-спрайт *(подробнее об этом методе ниже)*.  
Иконки из `src/img/icons` собираются в спрайт `build/img/sprite.svg`, по пути через svgo они очищаются от комментариев и пустых атрибутов, а плагин `svg-current-color` готовит их цвета к управлению из CSS.  

### svg-current-color
Плагин `svg-current-color` *(`gulp/plugins/svg-current-color/`, плагин для svgo)* меняет чёрные значения атрибутов `fill` и `stroke` *(`black`, `#000`, `#000000`, `rgb(0, 0, 0)`)* на `currentColor`. Цвет такой иконки задаётся CSS-свойством `color`.  
Остальные цвета не меняются, поэтому многоцветные иконки сохраняют свои цвета. `fill="none"` тоже остаётся на месте — контурные иконки *(с обводкой `stroke`)* не заливаются.  

#### Краткая инструкция/рекомендация  
*(при экспорте иконок из Figma)*
1. Необходимо собрать все используемые в дизайне иконки;
2. Иконки с обводкой можно экспортировать как есть — чёрная обводка тоже станет `currentColor`. Если толщина обводки должна масштабироваться вместе с иконкой при любом размере, примените `Outline stroke` *(Figma Menu ➔ Object ➔ Outline stroke)*;
3. Каждую иконку поместить в свой квадратный фрейм с подходящим названием *(рекомендую использовать именно квадратные фреймы, так как будет проще позже встраивать их на сайт)*;
4. Выделить все икноки и поменять их цвет *(кроме многоцветных)* на черный `#000000`;
5. Если иконка многоцветная, то поменять цвет на черный только в тех частях иконки, цвет которых необходимо будет менять средствами `CSS`;
6. Далее экспортируем иконки в формате svg в директорию `src/img/icons`;
7. Внутри данной директории можно создавать поддиректории, для сортировки иконок по значению *(в таком случае иконка будет доступна в `HTML/CSS` через конструкцию вида - `название_папки-название_иконки`)*;
8. После запуска сборки иконки будет доступны через спрайт `build/img/sprite.svg`;

#### Примеры вызова иконок  
**HTML**  
`<svg class="icon" width="32" height="32"><use href="img/sprite.svg#название_иконки"></use></svg>`  
**Класс `icon` является обязательным, на него завязаны технические стили для иконок*  
**Данную конструкцию можно быстро вызвать через сниппет svg*  

**CSS**  
`url(../img/sprite.svg#название_иконки)`

### Подробнее об svg-спрайтах
**SVG-спрайт** - это некий сборник всех иконок, которые нужны вам на сайте, они все собраны в одном svg-файле, но их можно вывести каждый отдельно, указав нужный идентификатор. Такой подход экономит ваше время и силы, а так же не оказывает негативного влияния на оптимизацию сайта.  

Основным преимуществом использования svg-спрайтов является возможность стилизовать иконки через CSS-стили. Мы можем менять размер, цвет, фон иконок, а также — менять стили при наведении.  


## Шрифты
В шаблоне реазиована автоматическая генерация шрифтов и сделаны заготовки под вызов и назначение шрифтов на сайте.

### Генерация файлов шрифтов
Первым делом вам необходимо положить шрифты формата `ttf` в папку `src/fonts/`. Сборка сконвертирует их в `woff2` и положит в `build/fonts/`. Уже готовые файлы `woff2` из `src/fonts/` копируются в `build/fonts/` без изменений.  
Если сборка уже запущена, то она распознает изменения в папке шрифтов и запустит задачу генерации. Если сборка не запущена, задачу можно запустить отдельно командой `pnpm font`.
> Конвертация шрифтов — самая долгая задача сборки, поэтому готовые `woff2` сохраняются в папку `.cache/fonts/`. Повторно конвертируются только новые и изменённые `ttf`, а при удалении `ttf` из `src/fonts/` его `woff2` удаляется из кэша. Если нужно пересобрать все шрифты заново, удалите папку `.cache/fonts/`.

### Подключение шрифтов
После генерации шрифтов нужно перейти в файл `src/scss/base/fonts.scss` и следуя инструкции внутри файла подключить добавленные шрифты.

### Назначение заготовок стилей шрифтов
Если вы верстаете сайт по макету из Figma, вероятнее всего там есть стили шрифтов, которые задает дизайнер с прямыми руками.  
Используя Figma-расширение `Global style to code`, вы можете скопировать эти стили в scss-формат и использовать их для быстрого вызова в шаблоне.  
Для этого есть файл `src/scss/abstracts/font-styles.scss`, в который и нужно вставить скопированные стили шрифтов. А затем привести их к общему виду, как в примерах в этом файле.  
Для вызова заготовок стилей, воспользуйтесь сниппетом `f`.

#### reductFont
**Данная функция работает в тестовом режиме, не гарантируется стабильность ее работы.**  
Функция `reductFont` позволяет минимизировать затраты времени на подгон шрифтов под мобильные устройства.  
Логика функции следующая: она берет изначальное значение шрифта и конвертирует его по своеобразной обратной геометрической прогрессии. Чем больше изначальное значение шрифта – тем большее значение отнимается от него для мобильной версии.  

На примере это выглядит так:
- Изначальный шрифт в `13px` становится `12px`;  
- Изначальный шрифт в `16px` становится `14px`;  
- Изначальный шрифт в `20px` становится `16px`;  
- Изначальный шрифт в `36px` становится `20px`;  
- Изначальный шрифт в `64px` становится `24px`;  
- И так далее..  

Это наиболее оптимальный вариант автоматического преобразования шрифтов для мобильных версий сайтов.

### Переключение языка
Пока мы далеко не отошли от темы сочетаний клавиш, поговорим немного о переключении раскладки клавиатуры.  
Если вы пользуетесь поиском Spotlight или переключением языка на MacOS по сочетанию `Command + Space`, то спешу вас огорчить, что это не эффективно *(это касается и Windows с его `Alt+Shift` или даже `Ctrl+Shift`)*. Самой быстрой кнопкой [на диком западе] для переключения языка *(по моему скромному мнению)* является `Caps Lock`.  

**Caps Lock на MacOS**  
Сделать переключение языка по нажатию `Caps Lock` на MacOS не сложно, это позволяет сделать сама система, через настройки клавиатуры. Но даже при таком *(казалось бы)* простом решении – есть косяк. Переключение очень часто опаздывает, и если вы быстро начнете печатать после переключения – выйдет бессмыслица, так как язык не успеет переключится. К тому же постоянно всплывающее окошко с оповещением о переключении раздражает.  
Выход есть, это <a href="https://github.com/Nikeev/LangSwitch" target="_blank">LangSwitch</a> *(не путать с Lang Switcher)* – небольшое приложение, которые убирает все задержки при переключении языка по клавише `Fn/🌐`.  Нам остается только поменять клавишу `Caps Lock` и `Fn` местами в настройках клавитауры MacOS и будет счастье.

**Caps Lock на Windows**  
Что касается Windows – тут немного сложнее. Из коробки он не дает возможности переключать языки по `Caps Lock`. Но это же Windows, для которой существуют сотни тысяч различных программ.  
Лично я настроил переключение языка на Windows по `Caps Lock` с помощью макросов клавиатуры, которая поддерживает VIA.  
Если у вас обычная клавиатура без макросов, то можно воспользоваться всем известным скриптовым языком <a href="https://www.autohotkey.com/" target="_blank">AutoHotkey</a>.

## Система маркеров задач
В шаблоне используется система маркеров задач, для ведения рабочего todo-листа. Для обработки маркеров необходимо установить VSCode-расширения `todo tree` и `todo highlight v2`. Все это будет работать после установки рекомендованных расширений.

### Как это работает?
В том месте, где нужно пометить себе задачу, прописать сниппет `com|todo`, который автоматически вставит комментарий с выбором маркера, в зависимости от расширения файла. Описать задачу после двоеточия и забыть про нее на какое-то время. А когда придет момент для правок, зайти в интерфейс `todo tree` расширения и закрыть все задачи (или не закрывать, решать вам).  

### Типы маркеров
Ниже представлен список типов маркеров, используемых в шаблоне и их предназначение:

🟡 **ЗАДАЧА:** - обычная задача, не требующая срочного вмешательства;  
🔵 **ДОРАБОТКА:** - задача, которая переносит работу "на потом";  
🔴 **СРОЧНО:** - задача, которая требует немедленного вмешательства;  
🟤 **КОСТЫЛЬ:** - напоминание о том, что тут есть костыль;  
🟠 **БАГ:** - напоминание о том, что тут есть баг;  
⚫ **TODO:** - просто маркер для отслеживания чужих задач;

## Полезные советы

### <h3 id="no-ua-sniffing">Как обойтись без определения браузера и системы</h3>

До версии 1.3.0 в шаблоне был модуль `detectUserInfo`, который вешал на `<body>` классы вида `system-win`, `system-iphone`, `browser-safari` — под них писали точечные стили. Такой подход себя не оправдывает: строка user-agent врёт *(iPad с iPadOS представляется как `Macintosh`, Chrome на iOS — как Safari, Android содержит `Linux`)*, а знать почти всегда нужно не название браузера, а конкретную возможность — есть ли мышь, поддерживается ли свойство, занимает ли скроллбар место. На эти вопросы CSS отвечает сам.

#### Мышь или палец: `@media (hover)` и `(pointer)`

Самая частая причина, по которой заводили классы устройств, — отделить десктоп от сенсорных экранов. Для этого есть медиа-функции:

```scss
// Наведение — только там, где есть настоящее наведение.
// На телефоне hover «залипает» после тапа, поэтому такие эффекты туда пускать не нужно
@media (hover: hover) {
	.card:hover .card__overlay {
		opacity: 1;
	}
}

// Грубый указатель — палец. Увеличиваем зону нажатия
@media (pointer: coarse) {
	.button {
		min-height: rem(48);
	}
}
```

`hover` отвечает на вопрос «может ли пользователь навести курсор», `pointer` — «насколько точен его указатель» *(`fine` — мышь или стилус, `coarse` — палец)*. Ноутбук с сенсорным экраном сообщит о себе честно, а user-agent об этом не скажет вообще ничего.

Важная деталь: открытие по `:hover` стоит **дополнять** фокусом, а не заменять им. Так компонент остаётся доступным с клавиатуры — именно так сделаны [тултипы](#tooltips) в шаблоне.

#### Высота экрана на мобильных: `dvh`, `svh`, `lvh`

Классический повод для `.system-iphone` — блок на весь экран, который «прыгает» в мобильном браузере из-за исчезающей адресной строки. Раньше это лечили хаком `height: -webkit-fill-available`. Сейчас есть единицы, которые учитывают панели браузера:

```scss
.promo {
	min-height: 100dvh; // dynamic — подстраивается под текущее состояние панелей
	// 100svh — минимальная высота (панели раскрыты), 100lvh — максимальная (панели скрыты)
}
```

#### Полоса прокрутки: `scrollbar-gutter`

Ещё один популярный случай — `.system-win`, потому что в Windows скроллбар занимает место, а в macOS он оверлейный и контент от него не сдвигается. Лечится одной строкой, которая уже стоит в `base/null.scss`:

```scss
html {
	scrollbar-gutter: stable; // место под скроллбар резервируется всегда, контент не дёргается
}
```

Если всё же нужна точная ширина в пикселях — её считает модуль [calcScrollbarWidth](#calcScrollbarWidth) и кладёт в переменную `--scrollbar-width`.

#### Поддержка возможности: `@supports`

`@supports` проверяет, **понимает ли браузер конкретное объявление** — не устройство и не название браузера. Это правильный инструмент, когда вы применяете что-то новое и хотите запасной вариант:

```scss
// Обычная сетка как запасной вариант
.gallery {
	display: flex;
	flex-wrap: wrap;
}

// И masonry там, где он уже есть
@supports (grid-template-rows: masonry) {
	.gallery {
		display: grid;
		grid-template-rows: masonry;
	}
}
```

Проверять можно и селекторы — например, есть ли у браузера псевдоэлемент для анимации спойлеров:

```scss
@supports selector(::details-content) {
	// анимация раскрытия
}
```

Условия комбинируются через `not`, `and` и `or`:

```scss
@supports not (animation-timeline: view()) {
	// оформление для браузеров без scroll-driven анимаций
}
```

В JS у этой проверки есть двойник — `CSS.supports()`. Шаблон использует его, чтобы не грузить лишние 60 КБ полифила там, где он не нужен *(см. `src/js/modules/index.js`)*:

```js
if (!CSS.supports('animation-timeline: view()')) {
	await import('../libs/scroll-timeline.js');
}
```

##### ❗️ПРИМЕЧАНИЕ
У `@supports` есть честное ограничение: он проверяет, что браузер **разобрал** объявление, а не что реализовал его без багов. Свойство может поддерживаться и при этом работать криво — как раз из-за таких случаев когда-то и появился user-agent-сниффинг.

Если дело дошло до починки конкретного движка, есть аварийный приём — проверка свойства, которое есть только в WebKit:

```scss
@supports (-webkit-hyphens: none) {
	// правило применится только в Safari
}
```

Это всё ещё определение браузера со всеми его минусами, поэтому прибегать к нему стоит в последнюю очередь и с комментарием, какой именно баг он обходит.
